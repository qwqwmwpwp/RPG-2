## 1. 交付物与完成标志对照

| 路线图完成标志 | 落盘实现 |
|---|---|
| **放得下吗** | `QuerySpace(startIndex, dimensions)` → `SpaceQueryResult<RuntimeItem>` |
| **放几个、剩多少** | `QueryAvailability(item)` / `FillAvailability(item, amount, result)` → `SlotAvailabilityResult<RuntimeItem>` |

## 2. 契约（API 一览）

| 成员 | 语义 | 复杂度 |
| --- | --- | --- |
| `InventoryContainer(rows, columns)` | 构造；非正尺寸、`rows × columns > MaxSlotCount`（65536）、长整型溢出一律抛 `ArgumentOutOfRangeException` | O(R×C)（初始化） |
| `TryGetPlacement(item, out placement)` | 物品 → 不可变放置记录（上左索引 + 冻结尺寸） | O(1) |
| `IsIndexOccupied / GetItemAt / GetUpperLeftIndexAt` | 单格读取 | O(1) |
| `GetItemDimensions(item)` | 读 `GridFragment.Width/Height`；缺失按 1×1（与源 `UMIS_InventoryGrid::GetItemDimensions` 一致） | O(1) |
| `QuerySpace(startIndex, dimensions)` | 悬停落点三分流：全空 → `HasSpace`；整块同属一个物品 → `CanSwap` 且 `UpperLeftIndex` 是该物品上左格；否则空结果 | O(W×H) |
| `QueryAvailability(item, amountOverride)` | 全网格行优先容量查询，分配新结果实例 | 最坏 O(R×C×W×H) |
| `FillAvailability(item, amount, result)` | 同上，但复用调用方结果实例（热路径零分配） | 同上 |
| `TryPlaceItem(item, startIndex, out error)` | 指定落点放置，不做堆叠 | O(W×H) |
| `TryRemoveItem(item, out error)` | 移除并释放全部格子 | O(W×H) |
| `TryStackItem(target, incoming, out movedCount, out error)` | 并入现有堆叠，可部分并入 | O(1) |
| `TryAddItem(item, out remainder, out error)` | 先并行优先堆叠、再落到首个空白区域 | 最坏 O(R×C×W×H) |
| `FillItemsByItemId(destination)` | 按 `ItemId` 升序输出物品（确定性顺序，供 M3 初始快照、日志与测试） | O(n log n) |
| `Revision` | 每次成功变更自增，供上层做变更检测 | O(1) |

`InventoryPlacement`：不可变放置记录（`Item` / `UpperLeftIndex` / `Dimensions` / `CellCount`），`Invalid` 表示空置格。

## 3. 数据不变量

1. **位置归数据层所有**（修正项 H）。源系统因为没有 UI 引用就在 `TryAddItem` 里直接 return 的临时方案**不复刻**。
2. **只有两份状态，且同源**：`cells[]`（逐格 `InventoryPlacement`，空置为 `InventoryPlacement.Invalid`）与 `placements`（`RuntimeItem` → 放置记录）；二者只在提交阶段由同一段代码写入——`CommitPlacement` 与 `ClearCells` 都经私有 `FillCells(startIndex, dimensions, value)` 落盘，`cells[]` 的唯一写入点即 `FillCells`。**没有第三份「物品列表」**——枚举直接用 `placements.Keys`。
3. **尺寸冻结在记录里**：占位尺寸在放置时写入 `InventoryPlacement.Dimensions`，移除按记录内尺寸释放，不重新向 `GridFragment` 取值。
4. **堆叠数单一来源**（修正项 K）：容量计算现取 `RuntimeItem.StackCount`，容器不缓存任何计数。
5. **矩形不重叠**：任何时刻同一格只属于一条放置记录。
6. **失败即零变更**：所有 `Try*` 先完成校验（`TryAddItem` 另加只读规划段）再进入提交段。

## 4. 偏差

### 4.1 照搬自蓝本的主动偏差（勿"改回源实现"）

| # | 偏差 | 理由 |
|---|---|---|
| 1 | **合并要求双方都可堆叠**（源只校验被占方） | 源的组合会把「不可堆叠物品并进可堆叠堆」，宁可拒绝 |
| 2 | **容量受被占堆自身上限约束**（源用待放物品上限） | 以既存堆叠上限为准 |
| 3 | **`TryAddItem` 为全量吸收** | M1 无「按类型实例化 / 拆分拷贝」工厂，装不下即整体失败零变更；需要部分接收时用 `QueryAvailability().Remainder` 与 `TryStackItem().movedCount` |
| 4 | **被完全并入的来源实例不清零** | M1 明确禁止堆叠数为 0，由调用方丢弃 |
| 5 | **不提供「原地移动」** | 物品已在容器内时 `TryPlaceItem` / `TryAddItem` 一律拒绝（搬运先 `TryRemoveItem`） |

### 4.2 本工程新增偏差：F6 事件总线广播（**本轮唯一功能性偏差**）

蓝本 M2 明确「只保证状态正确，变更广播留给 M4/M6」；RPG_4 的 F6 事件总线（`Core/Events/`）已在 F6 落盘，故本轮在**变更成功路径**按 §5 发送广播。注入点共 4 处、辅助方法 3 个（`NotifyItemAdded` / `NotifyItemRemoved` / `NotifyStackChanged`），无其它代码改动。**2026-10-06 精简重构后，注入点数、辅助方法数、广播次数与顺序、`source` 取值均未变（重构冻结项，见 §4.3）。**

- **source key = 容器实例（`this`）**：M2 是纯 C# 数据层，没有组件实例；容器实例作 source 同样满足「同键不同实例不串台」的表结构语义。**M3 引入 `InventoryComponent` 后必须一并定案**：source 是继续用容器实例，还是迁移到组件实例——否则 M5/M6 订阅方会与发送方 source 错配。
- **异常隔离**：F6 的 `EventBus` 已隔离单个回调异常（记 `Error` 并继续派发），故广播处不需要 `try/catch`，数据层状态不会被订阅方异常破坏。
- **广播只在变更成功路径**（查询路径完全不广播），因此悬停预览不会产生噪音。
- **双重广播风险（留给 M3）**：M3 的 `BackpackNetworkInventory` 若在复制回调里再次发布同类广播，需要去重，本轮只保证 M2 数据层是唯一发送方。

## 5. F6 广播契约（M2 发送方）

键取自 `Core/Events/EventChannels.cs`（禁止裸字符串）。

| 触发路径 | 键 | 载荷 | 说明 |
|---|---|---|---|
| `TryPlaceItem` 成功 | `InvChannels.ItemAdded` | `(RuntimeItem item)` | 物品进入容器 |
| `TryAddItem` 成功且发生落格（`placeIndex != NoIndex`） | `InvChannels.ItemAdded` | `(RuntimeItem item)` | 被收编后落到空白区；**纯并入既有堆叠时不发**（没有新条目） |
| `TryAddItem` 成功且并入过既有堆叠 | `InvChannels.StackChanged` | `(SlotAvailabilityResult<RuntimeItem>)` | 每个被并入的目标堆叠各发一次 |
| `TryStackItem` 成功 | `InvChannels.StackChanged` | `(SlotAvailabilityResult<RuntimeItem>)` | 目标堆叠增长（来源恒在容器外，无需广播其变化） |
| `TryRemoveItem` 成功 | `InvChannels.ItemRemoved` | `(RuntimeItem item)` | 物品离开容器（该键由本轮在 `InvChannels` 新增） |

`InvChannels.StackChanged` 的载荷由 `QueryAvailability(item)` 现算（只读扫描，最坏 O(R×C×W×H)，仅变更路径触发）。

## 6. 性能

- 单格读取、按物品定位：O(1)；悬停落点查询 O(W×H)、只读、零分配。
- 容量查询最坏 O(R×C×W×H)：行优先、轮次戳（`claimed[]` + `claimStamp`）跳过已检查区域、被占但非上左格的索引直接剪枝、`Remainder` 归零即提前退出。**刻意不引入**空间树 / 四叉树。
- 逐格扫描统一走私有 `ref struct RegionCursor`（2026-10-06 精简引入）：以「起点索引 + 尺寸」行优先推进，栈上结构、无委托无闭包、零堆分配；`QuerySpace` / 区域校验 / 区域标记 / 空区域判定 / 矩阵写入共用同一游标，尺寸非正时遍历为空（与原双层循环逐格等价）。
- 热路径无 LINQ、无闭包、无逐格临时集合；`FillAvailability` 复用调用方结果实例可做到逐帧零 GC。
- 日志只在**变更类**操作被拒时写（`Reject`），查询路径完全不写。
- 广播带来的额外成本：每次成功变更 1 次发布；`StackChanged` 额外一次只读容量扫描（变更路径，非逐帧）。

## 8. M3 边界与遗留

- `InventoryContainer` 不是 `MonoBehaviour`、也未标 `[Serializable]`：`RuntimeItem` 是纯 C# class，**不能**直接进 Mirror `SyncList`。M3 需要的是「投影」，不是「复用容器对象」。
- **身份**：M2 用 `RuntimeItem` 引用作容器内身份，依赖其**未重写 `Equals`/`GetHashCode`** 的引用语义。M3 必须投影为稳定 `ItemId`（`FillItemsByItemId` 已提供确定性顺序）。
- **候选投影面**：`InventoryPlacement` 已是「上左索引 + 尺寸」的不可变数据，可直接充当网络结构体字段来源；容器侧只需额外提供「稳定身份 + 集合增删事件」。
- **待定案**：广播 source key 是否从容器实例迁移到 `InventoryComponent`；M3 复制回调与 M2 广播的去重策略。
- `TryAddItem` 的全量吸收限制（§4.1 #3）需在 M6 处理「拾取超过上限的堆叠」时解除。
